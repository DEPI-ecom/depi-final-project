# Marketly — API Documentation

**Version:** 1.1 — updated to reflect the currently implemented User, Catalog, and Search services  
**Style:** REST + JSON  
**Development services:** User `http://localhost:3001`, Catalog `http://localhost:3002`, Search `http://localhost:3003`  
**Planned API Gateway:** `http://localhost:8080/api` (not implemented yet)  
**Payment:** Mock simulation only. No real gateway, card data, or provider webhooks.  
**Scope:** Current implementation plus planned contracts for Cart, Order, and Payment. The latter are not yet verified against implementation.

> **Implementation status:** Sections 2–4 describe the current User, Catalog, and Search service behavior based on the implementation completed so far. Sections 5–7 remain planned contracts for the services being developed separately. Do not treat planned endpoints as available until their services are implemented and tested.

## 1. Conventions

- During local development, the frontend calls User, Catalog, and Search directly on ports `3001`, `3002`, and `3003`. The API Gateway is planned but is not available yet.
- Once the Gateway is implemented, browser traffic should use the Gateway as the single public entry point.
- `Content-Type: application/json` for JSON requests.
- IDs are generated by the database (UUIDs in the current Prisma schemas).
- Prisma decimal product prices are serialized as decimal values/strings by the JSON response; clients should not use floating-point arithmetic for authoritative checkout totals.
- Catalog pagination defaults to `page=1` and `limit=10` in the current implementation. `limit` has a maximum of `50`.
- Protected User endpoints require `Authorization: Bearer <token>`.
- Current User auth responses return the JWT in the field `token` (not `accessToken`).
- Current successful responses generally use a `{ "data": ... }` envelope. Error responses use `{ "error": { "code, message, details } }`.

### Current error format

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "details": []
  }
}
```

The exact `details` contents depend on the validation/error path. A Gateway-generated `requestId` is not currently part of the established service contract.

### HTTP status codes

| Code | Meaning |
|---|---|
| 200 | Successful read/update/action |
| 201 | Resource created |
| 204 | Successful delete, if returned by the endpoint |
| 400 | Request validation failure |
| 401 | Missing/invalid authentication or invalid credentials |
| 404 | Resource not found |
| 409 | Conflict, such as duplicate email (where implemented) |
| 500 | Unexpected server error |
| 503 | Required downstream service unavailable (Search) |

## 2. Authentication and user profile — User Service

**Base URL:** `http://localhost:3001`  
**Database:** `users_db`  
**Authentication:** JWT bearer token on protected routes.

### `POST /auth/register`
Public. Creates a customer account.

Request (all four fields are required by the current implementation):
```json
{
  "name": "Alex Customer",
  "email": "alex@example.com",
  "phone": "+201000000000",
  "password": "StrongPassword123!"
}
```

The current response is wrapped in `data` and contains both the created `user` and a JWT `token`:
```json
{
  "data": {
    "user": {
      "id": "user-uuid",
      "name": "Alex Customer",
      "email": "alex@example.com",
      "phone": "+201000000000",
      "role": "CUSTOMER"
    },
    "token": "<jwt>"
  }
}
```

The password is hashed with bcrypt and must never be returned. Duplicate email and validation failures are returned through the service error handler.

### `POST /auth/login`
Public.

Request:
```json
{ "email": "alex@example.com", "password": "StrongPassword123!" }
```

Response:
```json
{
  "data": {
    "user": {
      "id": "user-uuid",
      "name": "Alex Customer",
      "email": "alex@example.com",
      "phone": "+201000000000",
      "role": "CUSTOMER"
    },
    "token": "<jwt>"
  }
}
```

**Important:** The field is `token`, not the previously proposed `accessToken`. Send it on protected requests as `Authorization: Bearer <token>`.

### `GET /users/me`
Customer. Returns the authenticated user's profile in the `data` envelope. The user identity is taken from the verified JWT, not from a user ID supplied by the browser.

### `PUT /users/me`
Customer. Updates editable profile fields. The user identity is taken from the verified JWT.

### `GET /users/me/addresses`
Customer. Lists saved addresses belonging to the authenticated user.

### `POST /users/me/addresses`
Customer. Creates an address.

Current address fields are:
```json
{
  "label": "Home",
  "recipientName": "Alex Customer",
  "phone": "+201000000000",
  "street": "12 Example Street",
  "city": "Giza",
  "state": "Giza",
  "postalCode": "12345",
  "isDefault": true
}
```

`state` and `postalCode` are optional in the current Prisma model. The old documented names `addressLine` and `country` are not the implemented field names. Do not send those old names unless the backend contract is deliberately changed.

### `PUT /users/me/addresses/:addressId`
Customer. Updates an address owned by the authenticated customer.

### `DELETE /users/me/addresses/:addressId`
Customer. Deletes an address owned by the authenticated customer. Confirm the exact status/body from the controller before relying on a `204 No Content` response in a client.

### User data model notes

- `User` includes `name`, unique `email`, `phone`, `passwordHash`, `role`, and timestamps.
- New users default to role `CUSTOMER`.
- `Address` includes `label`, `recipientName`, `phone`, `street`, `city`, optional `state` and `postalCode`, and `isDefault`.
- Addresses belong to a user and are deleted when their parent user is deleted.

## 3. Catalog — Catalog Service

**Base URL:** `http://localhost:3002`  
**Database:** `catalog_db`  
**Authentication:** Product and category read endpoints are public.

### `GET /products`
Public. Returns active products with category information and pagination.

Query parameters:

| Parameter | Description | Current validation/default |
|---|---|---|
| `q` | Keyword in product name or description | Optional; trimmed, case-insensitive contains match |
| `categoryId` | Filter by category ID | Optional |
| `minPrice` | Minimum price | Optional number, minimum `0` |
| `maxPrice` | Maximum price | Optional number, minimum `0` |
| `page` | Page number | Positive integer, default `1` |
| `limit` | Page size | Integer `1`–`50`, default `10` |
| `sort` | Sort order | `newest`, `price_asc`, `price_desc`, `name`; default `newest` |

If both price bounds are supplied, `minPrice` must not exceed `maxPrice`.

Example:
`GET /products?q=headphones&categoryId=category-uuid&minPrice=10&maxPrice=100&page=1&limit=10&sort=price_asc`

Current response shape:
```json
{
  "data": {
    "products": [
      {
        "id": "product-uuid",
        "name": "Wireless Headphones",
        "description": "Over-ear wireless headphones",
        "price": "79.99",
        "stock": 14,
        "imageUrl": null,
        "categoryId": "category-uuid",
        "category": {
          "id": "category-uuid",
          "name": "Electronics",
          "slug": "electronics"
        }
      }
    ],
    "pagination": {
      "page": 1,
      "limit": 10,
      "total": 1,
      "totalPages": 1
    }
  }
}
```

The exact product values depend on the database seed/data. The current Prisma model uses `stock` (not the proposed `stockQuantity`) and `price` is a Prisma Decimal.

### `GET /products/:productId`
Public. Returns one active product, including its category, wrapped as `data.product`:
```json
{
  "data": {
    "product": {
      "id": "product-uuid",
      "name": "Wireless Headphones",
      "description": "Over-ear wireless headphones",
      "price": "79.99",
      "stock": 14,
      "imageUrl": null,
      "category": {
        "id": "category-uuid",
        "name": "Electronics",
        "slug": "electronics"
      }
    }
  }
}
```

Returns `404` with code `PRODUCT_NOT_FOUND` if the product does not exist or is inactive.

### `GET /categories`
Public. Returns categories with active product counts. The response is wrapped in `data`; use the actual returned category fields (`id`, `name`, `slug`, and count where included) rather than relying on the older bare-array example.

### Catalog data model notes

- `Category`: `id`, `name`, unique `slug`, optional `description`, timestamps.
- `Product`: `id`, `name`, unique `slug`, `description`, Decimal `price`, integer `stock`, optional `imageUrl`, `isActive`, `categoryId`, timestamps.
- Only active products are returned by the public product listing/detail endpoints.
- Seed data currently includes Electronics, Clothing, and Home and Living categories, with sample products.
- The current public implementation does not include the proposed `/internal/stock/*` endpoints. Those remain future work for Order/Cart integration.

## 4. Search — Search Service

**Base URL:** `http://localhost:3003`  
**Database:** No separate database. Search forwards requests to Catalog.

### `GET /search`
Public. Accepts the same filtering and pagination query parameters as Catalog and forwards them to the Catalog product-list endpoint.

Query parameters:
- `q` optional keyword
- `categoryId` optional category ID
- `minPrice`, `maxPrice` optional numeric bounds
- `page` positive integer, default `1`
- `limit` positive integer, Search validator maximum `100`; Catalog currently enforces a maximum of `50`, so the effective maximum is `50`
- `sort`: `newest`, `price_asc`, `price_desc`, or `name`

The keyword is optional. If omitted, Search can still return products filtered by category/price/pagination because the request is forwarded to Catalog.

Example:
`GET /search?q=headphones&categoryId=category-uuid&minPrice=20&maxPrice=150&page=1&limit=10&sort=newest`

Success: Search returns the Catalog response body and status unchanged. Therefore the response has the same structure as `GET /products`, including `data.products` and `data.pagination`.

If Catalog cannot be reached or the upstream request times out, Search returns `503` with a service-unavailable error. The Search service uses a 5-second upstream timeout.

### `GET /health`
Returns the Search service health status. The current health response identifies the service as `search`.

### Search implementation notes

- Search has no Prisma schema or database of its own.
- Search calls Catalog's public `GET /products` endpoint; it does not call the previously proposed `/internal/products/search` route.
- Keyword matching is implemented by Catalog against product `name` and `description`, using case-insensitive contains matching.
- Supported sort values are aligned with Catalog: `newest`, `price_asc`, `price_desc`, and `name`. The previously proposed `relevance` sort is not implemented.

## 5. Cart — Cart Service

All endpoints require customer authentication. The service derives `userId` from the verified JWT.

### `GET /cart`
Returns the current customer's cart.

`200 OK`:
```json
{
  "data": {
    "id": "cart-uuid",
    "items": [
      {
        "id": "cart-item-uuid",
        "productId": "product-uuid",
        "quantity": 2,
        "product": {
          "name": "Wireless Headphones",
          "price": "79.99",
          "imageUrl": "https://example.com/headphones.jpg",
          "stockQuantity": 14
        },
        "lineTotal": "159.98"
      }
    ],
    "subtotal": "159.98",
    "currency": "USD"
  }
}
```

The product summary may be fetched from Catalog. Cart total is preliminary and must be recalculated at checkout.

### `POST /cart/items`
Adds a product or increases its existing quantity.

Request:
```json
{ "productId": "product-uuid", "quantity": 1 }
```

Response: `201 Created` or `200 OK` if updating an existing cart line. Return updated cart.

Errors: `400`, `404 PRODUCT_NOT_FOUND`, `409 INSUFFICIENT_STOCK`.

### `PUT /cart/items/:itemId`
Changes quantity.

Request:
```json
{ "quantity": 3 }
```

Response: `200 OK` with updated cart. Quantity must be a positive integer. A quantity of zero should use DELETE.

### `DELETE /cart/items/:itemId`
Removes a cart line. `204 No Content`.

### `DELETE /cart`
Clears the customer's cart. `204 No Content`. Used after successful checkout.

## 6. Orders and checkout — Order Service

All customer endpoints require authentication. A customer may only access their own orders.

### `POST /orders/checkout`
Creates an order and runs the mock checkout flow.

Headers:
```http
Authorization: Bearer <token>
Idempotency-Key: <unique-value>
Content-Type: application/json
```

Request:
```json
{
  "addressId": "address-uuid",
  "mockPaymentOutcome": "SUCCESS"
}
```

`mockPaymentOutcome` is `SUCCESS` or `FAILURE`. This field exists only for the educational mock flow and must be clearly labelled as a simulation in the UI. The Order service fetches the cart, current product prices and stock, and address details from their owning services. Never trust a client-supplied total or product price.

Successful mock payment: `201 Created`:
```json
{
  "data": {
    "order": {
      "id": "order-uuid",
      "status": "PAID",
      "subtotal": "159.98",
      "total": "159.98",
      "currency": "USD",
      "items": [
        {
          "productId": "product-uuid",
          "productName": "Wireless Headphones",
          "unitPrice": "79.99",
          "quantity": 2,
          "lineTotal": "159.98"
        }
      ],
      "createdAt": "2026-11-26T10:30:00.000Z"
    },
    "payment": {
      "id": "payment-uuid",
      "status": "SUCCEEDED",
      "mockReference": "MOCK-abc123"
    }
  }
}
```

Failed mock payment: return a created order with `PAYMENT_FAILED` status and a failed payment record. The API may use `201 Created` because the order and payment attempt were recorded; keep this consistent.

```json
{
  "data": {
    "order": {
      "id": "order-uuid",
      "status": "PAYMENT_FAILED",
      "total": "159.98",
      "currency": "USD"
    },
    "payment": {
      "id": "payment-uuid",
      "status": "FAILED",
      "mockReference": "MOCK-def456",
      "failureReason": "Simulated payment failure"
    }
  }
}
```

Errors:
- `400 VALIDATION_ERROR`
- `401 UNAUTHORIZED`
- `404 ADDRESS_NOT_FOUND` or `CART_NOT_FOUND`
- `409 EMPTY_CART`, `INSUFFICIENT_STOCK`, `IDEMPOTENCY_CONFLICT`
- `503 DEPENDENCY_UNAVAILABLE`

Retry behavior: for the initial version, define either `POST /orders/:orderId/retry-payment` with a new idempotency key and mock outcome, or require the customer to retry checkout from the retained cart. Recommended simpler choice: support retry on the existing failed order so it does not create duplicate orders. If implementing this route, validate that the order belongs to the customer and is `PAYMENT_FAILED`.

### `GET /orders`
Customer. Lists the authenticated customer's orders, newest first.

Query: `page`, `limit`, optional `status`.

`200 OK`:
```json
{
  "data": [
    {
      "id": "order-uuid",
      "status": "PAID",
      "total": "159.98",
      "currency": "USD",
      "createdAt": "2026-11-26T10:30:00.000Z"
    }
  ],
  "meta": { "page": 1, "limit": 12, "total": 1, "totalPages": 1 }
}
```

### `GET /orders/:orderId`
Customer. Returns order details, item snapshots, shipping snapshot, total, payment/order status. Only the owning customer may access it.

### `GET /orders/:orderId/status`
Customer. Returns a minimal status payload:
```json
{
  "data": {
    "orderId": "order-uuid",
    "status": "PAID",
    "updatedAt": "2026-11-26T10:35:00.000Z"
  }
}
```

Suggested order statuses for the initial project:
- `PENDING_PAYMENT`
- `PAID`
- `PAYMENT_FAILED`
- `CANCELLED`

Do not introduce shipping statuses such as `IN_TRANSIT` unless shipping/fulfilment is actually implemented. “Order tracking” in this scope means viewing the order's current processing/payment status.

## 7. Mock Payment — Payment Service

Payment service is internal to the application. A customer normally initiates payment through Order checkout, not by directly calling Payment.

### Internal `POST /internal/payments/mock`
Called by Order service.

Request:
```json
{
  "orderId": "order-uuid",
  "userId": "user-uuid",
  "amount": "159.98",
  "currency": "USD",
  "outcome": "SUCCESS"
}
```

Response:
```json
{
  "data": {
    "id": "payment-uuid",
    "orderId": "order-uuid",
    "status": "SUCCEEDED",
    "mockReference": "MOCK-abc123",
    "amount": "159.98",
    "currency": "USD"
  }
}
```

For `outcome: "FAILURE"`, record `FAILED` and return a safe reason such as `"Simulated payment failure"`.

Rules:
- Accept only `SUCCESS` or `FAILURE`.
- Generate the mock reference on the server.
- Do not accept card details.
- Do not expose this internal endpoint to browsers.
- Prevent duplicate successful mock payments for one order.
- Validate amount and order ID format.
- This is a simulation, not a secure payment processor.

### Optional customer-safe endpoint

`GET /payments/:paymentId` may be exposed through the gateway only if customers need payment status/history. Verify ownership using the authenticated user. Otherwise, expose payment information through `GET /orders/:orderId` and omit this public route.

## 8. Health and metrics — every backend service and gateway

### `GET /health`
No authentication. Lightweight liveness/health response.

```json
{
  "status": "ok",
  "service": "ecom-user"
}
```

Optionally include dependency status for readiness, but avoid making liveness fail just because a downstream service is temporarily unavailable.

### `GET /metrics`
No user authentication on the internal network; do not expose publicly without protection. Returns Prometheus text exposition format, using `prom-client`.

Recommended metrics:
- HTTP request count by method/route/status.
- HTTP request duration histogram.
- Process metrics.
- Optional business counters for checkout, mock payment results and stock conflicts.

## 9. Internal service endpoints

These endpoints are private to the application network and should not be proxied publicly unless deliberately needed.

| Caller | Target | Endpoint | Purpose |
|---|---|---|---|
| Search | Catalog | `GET /internal/products/search` | Search/filter catalog |
| Cart | Catalog | `GET /internal/products/:id` | Validate product and show current summary |
| Order | Cart | `GET /internal/cart` | Retrieve customer's cart (forward trusted user identity/token) |
| Order | User | `GET /internal/users/:id/addresses/:addressId` | Validate and fetch address snapshot |
| Order | Catalog | `POST /internal/stock/validate` | Check stock and obtain current price |
| Order | Payment | `POST /internal/payments/mock` | Record mock payment outcome |
| Order | Catalog | `POST /internal/stock/confirm` | Deduct/confirm stock after success |
| Order | Cart | `DELETE /internal/cart` | Clear cart after success |

Implementation note: the exact internal authentication mechanism must be agreed before coding. For this course prototype, forward the verified customer JWT between trusted internal calls and have target services verify it, or use a narrowly scoped internal service token. Do not blindly trust a user ID header supplied by the public browser.

## 11. Contract decisions developers must keep consistent

Before implementation, agree on:
1. Whether responses always use `{ "data": ... }` and how list pagination metadata is represented.
2. Exact query parameter names (`categoryId`, `minPrice`, `maxPrice`, etc.).
3. Exact order/payment status enum values.
4. Whether failed checkout creates a `PAYMENT_FAILED` order (recommended) and how retry works.
5. Whether stock is reserved before mock payment or rechecked and deducted after success.
6. How internal service calls authenticate the customer/service identity.
7. Currency and decimal precision.
8. Whether `GET /payments/:paymentId` is needed publicly.

Update this document when the agreed contract changes; do not let each service invent its own incompatible response shape.
